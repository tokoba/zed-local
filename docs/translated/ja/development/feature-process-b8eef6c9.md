# Zed の機能開発プロセス

これは中〜大規模の機能向けです — 新しい UI、挙動の変更、あるいは Zed の複数の部分にまたがる作業などを想定しています。小さなキーバインドの追加や設定の微調整のようなものについては、ここで説明するすべてのプロセスを踏む必要はありません。

> **始める前に:** 外部コントリビューターの場合は、大きな労力をかける前に、その機能がチームの望むものかどうか必ず確認してください。Please read the [Contributing Guide](../../../CONTRIBUTING.md) and our [Feature Request Guidelines](https://github.com/zed-industries/zed/discussions/51422) — if there isn't already a GitHub issue with clear staff confirmation, start with a GitHub Discussion. Feature request PRs that skip this process have a *very* low merge rate. Taking the time to follow our process significantly increases the chances your idea gets picked up and built.

## 1. なぜこれが重要なのか？

すべての機能はアイデアから始まります。コードを書く前に、そのアイデアを次の点でしっかり固めましょう:

- **これはどんな問題を解決するのか？**
- **その根拠は何か？** GitHub issue、Discord でのリクエスト、👍 の数、ブログ記事など。
- **先行事例はあるか？** VS Code、JetBrains、Neovim、あるいは非常に人気のあるプラグインに同様のものがあれば、それは強いシグナルです。アイデアがより独創的な場合でも、それが何をベースにしているのかを明示してください — 「これは X を Zed の multi-buffers 用にアダプトしたものです」のような説明は、「こういうのがあったらクールだと思う」のような説明よりもずっと有用です。

## 2. それは何か？

短く具体的な機能の説明文を書き、上で集めたコンテキストでそれを補強してください。数文でその機能を説明できない場合、その機能は大きすぎるか、あいまいすぎる可能性があります。

以下はフォーマットの一例ですが、あなたの機能に合わせて自由に調整してください。

**機能:** Inline Git Blame

**目的:** 各行について、エディタのテキスト直後に最後のコミットの作者とメッセージを表示し、開発者が git blame を開かずにコードの履歴を把握できるようにする。

**背景:**
これは主要なコードエディタではどこでも一般的に提供されている機能です:

- \[VS Code のスクリーンショット]
- \[Intellij のスクリーンショット]
- \[Neovim のスクリーンショット]
- そして、この [github issue](https://github.com) では 146 件の賛成（thumbs up）を獲得しています。

**決定事項:**
git CLI を使うか、git ライブラリを使うかを決める必要があります。Zed は git ライブラリを使用していますが、その blame の実装はコードエディタで使うには遅すぎるため、CLI の porcelain インターフェイスを使うべきです。

## 3. 他に何に影響するか？

実装を始める前に、このリストを一通り確認してください。すべてが当てはまるわけではありません:

- **アクションとキーバインド。** あなたの機能はどのようなアクションを定義しますか？デフォルトのキーバインドは既存のものと衝突していませんか？
- **設定。** 何か挙動は設定可能か？ユーザー単位か、プロジェクト単位か、言語単位か？新しい設定を Settings UI に追加するのを忘れないでください。
- **テーマとスタイリング。** 新しいセマンティックトークンが必要か？ライトモードとダークモードの両方で正しく表示されるか？
- **Vim モード。** Vim ユーザーはこの機能に対して異なる期待を持っているかもしれません。
- **リモート開発。** あなたの機能はリモートプロジェクトでも動作するか？ファイルパス、シェルコマンド、環境変数などは挙動が異なる可能性があります。
- **再起動をまたぐ永続性。** あなたの機能の状態は再起動後も保持されるべきか？
- **アクセシビリティ。** キーボードだけで操作できるか？フォーカス状態は明確か？
- **プラットフォームの違い。** macOS、Linux、Windows で挙動は異ならないか？
- **パフォーマンス。** 大きなファイルや大規模なプロジェクトでどのように動作するか？操作は即時に反応するか？
- **セキュリティ。** この機能は Workspace Trust とどのように相互作用するか？Zed に新たな攻撃面を作ってしまわないか？

あなたの機能が特に **エディタ** に関わる場合: エディタには多数の機能が共存しています — ガター要素、インラインブロック、マルチカーソル、折りたたみ、編集予測、コードインテリジェンスのポップオーバー、ミニマップなどです。これらをさまざまな組み合わせで有効にした状態で変更をテストしてください。通常のバッファで動作する機能でも、マルチバッファでは無効化する必要があるかもしれません。

## 4. 仕上げてリリースする

ここでまとめた内容を、GitHub Discussion、issue、あるいは PR の説明文の土台として使ってください。良いプロダクトリサーチは、目標、現在の到達点、そして検討すべきトレードオフについて、関係者全員の認識をそろえるのに役立ちます。
